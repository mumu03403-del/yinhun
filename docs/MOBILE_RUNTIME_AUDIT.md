## 0. 证据分级说明（重要）

| 标记 | 含义 |
|---|---|

## 2. 发现清单

### P1-1　「重置存档」按钮高度不足 44px【实测】

- **现象**：`RESET_BTN.h = 38`（行 77），低于 Apple HIG 与 WCAG 2.5.8 的 **44×44 CSS px** 下限。
  经缩放后实际屏幕高度更小：375 宽的机型 ≈ **35.6px**，390 宽的机型 ≈ **37.1px**。
- **影响**：底部边缘的按钮偏薄，手指容易点不中或误触到旁边的空白。
- **最小修复**：`RESET_BTN.h` 由 38 提到 **48**（同时把 `y` 由 `H-62` 改为 `H-72`，往上让出空间）。
  注意：加高后必须复核 §3 的底部安全余量是否仍为正。

### P1-2　`viewport-fit=cover` 生效，但**全文件没有任何 safe-area 适配**【实测 + 推断】

- **实测**：行 5 的 viewport 里写了 `viewport-fit=cover`（主动伸进刘海/Home 条区域），
  但全文**搜不到任何 `env(safe-area-inset-*)` 引用**，也没有任何手动让位的代码。
- **实测（顶部，确定性几何计算）**：375×812、安全区顶部 47px 时，顶部不安全区对应的逻辑 y 约 `< 22.5`。
  - 图鉴按钮顶边逻辑 `y=14` → 屏幕 y≈39 → **侵入不安全区约 8px**
  - 金币图标顶端逻辑 `y=16` → 屏幕 y≈41 → 侵入约 6px
  - 「金币」标签逻辑 `y=17` → 屏幕 y≈42 → 侵入约 5px
- **实测（底部，确定性几何计算）**：重置按钮底边逻辑 `y=788`，与底部安全线的逻辑位置比较：

| 设备（视口） | scale | 底部安全线对应逻辑 y | 重置按钮底边 788 | 结论 |
|---|---|---|---|---|
| iPhone X 375×812 | 0.936 | 803.4 | 788 | 安全，余量 ≈14.4 屏幕 px |
| iPhone 12/13 390×844 | 0.976 | 803.5 | 788 | 安全，余量 ≈15.1 屏幕 px |
| 14 Pro Max 430×932 | 1.083 | 805.1 | 788 | 安全，余量 ≈18.4 屏幕 px |
| Android 360×640（假设导航条 48px） | 0.759 | 764.6 | 788 | **被压 ≈17.8 屏幕 px** |

- **【推断】**：底部那条「安卓 360×640 被压」取决于**该系统导航条是否真的覆盖视口**。
  带底部导航条的安卓上很可能会压住按钮；手势导航或导航条不覆盖视口时不成立。**需真机确认。**
- **最小修复**：在 `resize()` 中读出安全区（用 `env()` 或 `visualViewport`），
  把 `view.oy` 的上偏移加上 `safeTop`、可用高度减去 `safeBottom`；
  或先用最省事的做法——底部 UI 整体按 `safeBottom` 上移。

### P2-1　DPR 已封顶为 3【实测】

- 行 281 明确 `Math.min(devicePixelRatio, 3)`，**没有失控风险**。
- 430×932 @dpr3 时后备缓冲 = 1290×2796 ≈ **3.61M 像素 ≈ 14.4 MB**（单次分配）。
  对现代手机可接受，**仅记录，不建议改**。

### P2-2　窄屏等比缩放会把全部触控目标缩到 44 以下【实测】

320×568（iPhone SE 一代）时 `scale = 0.6699`：

| 目标 | 逻辑尺寸 | 屏幕尺寸 | 是否 ≥44 |
|---|---|---|---|
| 重置存档 | 124×38 | 83×**25.5** | 否 |
| 招募 | 164×56 | 110×**37.5** | 否 |
| 图鉴 | 74×46 | 50×**30.8** | 否 |
| 关闭（图鉴面板） | 160×48 | 107×**32.2** | 否 |

- **原因**：整体等比缩放（行 288），小屏一律缩水，不是控件本身设计得过小。
- **最小修复**：触控命中的**判定区**与**绘制区**解耦——判定区设下限
  `max(44/scale, 设计值)`，绘制仍按设计值。这样小屏也能点准。

### P2-3　小游戏侧**完全没有「重置存档」功能**，适配层也没有确认框能力【实测】

- 行 347 用的是 `window.confirm('确定要清空存档…')` —— 这是浏览器专有 API。
- 实测：`build/minigame/game.js` 里**只有 `save`，没有任何 reset 逻辑**；
  `js/platform-wx.js` 与 `js/platform-h5.js` 里**都没有 `confirm` / `showModal` / `alert`**。
- **准确结论**：这是**功能缺口**，不是「会误删存档的 bug」——小游戏版目前根本没有重置入口。
- **最小修复**：下一步移植 `wx.showModal` 到 `platform-wx.js`（H5 侧映射到 `window.confirm`），
  再把重置流程接上。**不阻塞当前 H5 上线。**

### P2-4　横屏未做处理【实测·截图为证】

- 证据：`build/_evidence/mobile_audit/landscape_812x375_dpr3.png`
- H5 未锁方向；812×375 时 `scale = 0.4323`，画面缩到约 43%，两侧大片留黑。
- `build/minigame/game.json` 里声明了 `portrait`，但那只对小游戏生效，管不到浏览器。
- **最小修复**：横屏时叠加一个「请竖屏使用」提示层，而不是把游戏缩小。

## 3. 审计确认**没有问题**的部分（避免团队重复怀疑）

以下均为【实测·源码核对】；其真机表现仍属【推断】，但防护措施齐备：

- 长按结算所需的默认行为防护**全部就位**：`touch-action:none`（行 19）、
  `-webkit-touch-callout:none`（行 16）、`user-select:none`（行 15）、
  `-webkit-tap-highlight-color:transparent`（行 14）、`contextmenu` 已 `preventDefault`（行 409）。
  → 长按 0.5 秒结算**大概率不会被系统菜单/文字选择打断**。
- `pointerdown/move/up/cancel` 四个事件齐全且都调用了 `preventDefault`（行 324/358/372/403），
  手指拖出屏幕外有 `pointercancel` 兜底。
- DPR 有封顶（行 281）。
- 多数触控目标**达标**：招募 164×56、关闭 160×48、开始游戏 255×44、图鉴 74×46。
